## Purpose
This document explains the end-to-end journey of creating a fine-tuned GPT-4o model on Azure OpenAI to:  
- detect AI-generated content in student submissions,  
- grade them against rubrics, and  
- measure revision alignment.  

It covers technical decisions, data preparation, fine-tuning, testing, evaluation, and next steps.

---

## Introduction
The project’s goal was to build the foundation of a fine-tuning model for **AAIE** using **Azure AI** (as a foundation for future cohorts) capable of:
- **AI Content Detection** — identifying sentences likely generated by large language models.
- **Rubric-Based Grading** — assigning scores and constructive feedback per rubric criterion.
- **Revision Alignment** — measuring how closely a student’s final submission aligns with earlier drafts.

The vision is to reduce manual marking effort while keeping grading **transparent and fair**.

---

## Data Collection and Organization
We gathered **50 JSON files** (10 each for **5 domains**), each describing real assignments and grading details.

**Each file included:**
- **Assignment Prompt** — the question to be answered.  
- **Rubric** — criteria, weights, performance descriptors.  
- **10 Student Submissions** — final answers.  
- **Revision Chains** — drafts leading to the final submission.  
- **Hybrid Breakdown** — when available, paragraph-level AI vs human tags.  
- **Feedback** — past comments and scores.

Files followed a simple naming convention (e.g., `rub_teaching_0016.json`) as set by the data team, enabling easy batch processing.

---

## Data Preprocessing and JSONL Generation
A Python pipeline converted the raw JSON into the **`.jsonl`** format required by Azure OpenAI.

**Key actions:**
- Iterated through each JSON file and extracted key sections.
- Built a **prompt** with assignment, rubric, submission, and revision info.
- Built a **completion** containing the desired structured JSON:
  - `ai_detection`
  - `rubric_scores`
  - `revision_alignment`
  - `total`

**Result:** a clean, standardized dataset of **504 training examples**.

---

## Train / Validation / Test Splits
To enable robust training and evaluation, the dataset was split **80/10/10**:

- **Training:** 403 samples  
- **Validation:** 50 samples  
- **Test:** 51 samples

This supports dependable model assessment and future experimentation.

---

## Fine-Tuning on Azure (Configuration & Rationale)
Using the prepared `.jsonl` files, we fine-tuned GPT-4o on Azure with:

- **Epochs = 4** — deliberately low to avoid overfitting on a moderate dataset (~400 train samples).  
- **Learning rate = 0.1** — an initial aggressive value to help the model quickly adapt to our strict output schema; can be reduced in future runs to refine performance.  
- **Batch size = 16** — a balanced choice for GPU memory and stable gradient estimates.  
- **Validation set included (50 examples)** — Azure evaluated the model on a held-out validation set each epoch to monitor loss and prevent divergence.  
- **Live training logs (Azure Portal)** — tracked training/validation loss, token usage, and epoch progress in real time.  
- **Automatic deployment** — once training finished, Azure deployed the fine-tuned model for immediate inference.

> These choices were intentionally conservative for a first production pipeline: fewer epochs to avoid memorization, reasonable batch size, and a validation loop to catch early issues.

---

## Tracking Training Metrics (CSV)
To understand learning behavior, we exported **training vs validation metrics** to `training_vs_validation.csv`.

**The CSV captures:**
- **Training loss per step/epoch** — how the model fits training data.  
- **Validation loss per epoch** — generalization behavior on held-out data.  
- **Step/Epoch progression** — to spot underfitting/overfitting patterns.

Observation: over **4 epochs**, losses decreased consistently with **no overfitting spikes**. The CSV provides a transparent, reproducible record of fine-tuning performance.

## Testing and Evaluation
After fine-tuning, a test harness was used to:

- Load the hold-out test set (`test.jsonl`).
- Query the fine-tuned model with schema-enforcing prompts.
- **Force strict JSON** outputs for downstream reliability.
- Compute key metrics:
  - **F1 score** for AI detection.
  - **Mean Absolute Error (MAE)** for total score and revision alignment (when comparable).

### Metrics and Interpretation

**Aggregate evaluation results:**

- **AI Segment F1 Average:** `0.625` (≈62.5% overlap with ground-truth AI segments)  
- **Total Score MAE:** `None`  
- **Alignment % MAE:** `None`  

**Why “None”?**  
Many ground-truth items lacked numeric `total` scores and/or `revision_alignment` percentages.  
Because of this, the script couldn’t compute error values for those metrics.  
This is expected for an early experiment — once more labeled numeric data is added, the script will produce real MAE values.

**CSV reporting**  
A detailed per-sample CSV (`ft_eval_report.csv`) is generated for auditing:
- Per-example status (ok/error)
- AI detection precision / recall / F1
- Per-criterion absolute errors (when comparable)
- Normalized JSON outputs (truncated for readability)

### Future Improvements

- Add **numeric total scores** in ground truth to measure grade accuracy (MAE)  
- Annotate **revision alignment percentages** to train/validate that metric  
- Increase dataset **size** and **topic diversity**  
- Tune training hyperparameters (epochs, LR schedules, batch size)  
- Standardize post-processing (always numeric points, avoid qualitative bands like “Excellent”)  

---

### Lessons Learnt

- Clean, standardized data significantly simplifies fine-tuning  
- Enforcing **strict output schemas** early prevents integration issues later  
- Using a **hold-out test set** reveals labeling gaps before scaling up  
- Azure OpenAI fine-tuning is reliable when JSONL is **well-formed and consistent**
