# Evaluating LLM Generated Feedback

**Version:** 1.1 - Updated to include G-Eval
**Date:** December 2025
**Author:** Steven Christolis

The current feedback generation process uses an LLM to generate feedback based on the input of a submission and an associated rubric (the **Feedback LLM**).

One approach to evaluating the feedback produced is to use another LLM to evaluate the feedback produced. This is known as the **LLM-as-judge** pattern (the **Judge LLM**).

The Judge LLM requires its own rubric in order to judge whether the feedback generated is *good feedback*. 

As the Judge LLM is acting as a human evaluator, the criteria it will use is the same as if a human were performing the evaluation. It will be instructed to provide feedback based on the same criteria the human evaluator would use and be in the form of a feedback evaluation rubric.

This second rubric is known as a meta-rubric and typical dimensions might include:

| Dimension                            | Description                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| **Accuracy**                         | Does the feedback correctly reflect the student’s submission?                  |
| **Specificity**                      | Is the feedback concrete and supported with examples rather than vague advice? |
| **Constructiveness**                 | Does the feedback guide the student on how to improve?                         |
| **Alignment with assignment rubric** | Does the feedback actually reference the criteria used to judge the work?      |
| **Tone and clarity**                 | Is the feedback easy to understand and supportive?                             |

This rubric is a simplified version of the **ReviewEval** [1] framework.

This Judge LLM can be used to evaluate both human generated feedback and that generated by the Feedback LLM. 

The criteria in the second rubric are universal standards for quality feedback regardless of who created the feedback.

## 1. Comparison to other Evaluation Metrics

The following table compares metrics calculated in previous iterations of the AAIE product to LLM-as-judge approach.

| Feature              | LLM Metrics (BLEU, ROUGE)                                                          | Semantic Metrics (BERTScore)                                                 | LLM-as-Judge (LLM Evaluation)                                                                  |
| -------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **What it measures** | Exact word/phrase overlap (Syntax).                                                | Meaning similarity (Semantics).                                              | Quality, reasoning, tone, and helpfulness.                                                     |
| **Requirement**      | Requires a "Gold Standard" reference text (a perfect answer to compare against).   | Requires a "Gold Standard" reference text.                                   | Does **not** strictly require a reference text; can evaluate based on rubric criteria alone.   |
| **Strengths**        | Fast, cheap, objective, reproducible.                                              | Better than n-grams at catching synonyms and paraphrasing.                   | Can assess complex nuances like "Tone," "Actionability," and "Empathy." Mimics human judgment. |
| **Weaknesses**       | Penalizes good answers that use different words. Blind to "Tone" or "Helpfulness." | Still relies on reference proximity; cannot judge if advice is "actionable." | Slower, more expensive (API costs), and can be biased or inconsistent (hallucinations).        |

The main advantage of the LLM-as-Judge is that it does not need a reference text (or ground truth), it can evaluate on rubric criteria alone.

This means that LLM-as-Judge can be used to evaluate LLM generated feedback without having feedback ground truth for the evaluation.

## 2. Use an LLM-as-a-judge pattern

A common evaluation design which aligns with the Feedback Generation use case is:

1. **Provide the evaluation LLM with:**
   
   - the student’s submission
   
   - the assignment rubric
   
   - the generated feedback
   
   - the *meta-feedback rubric* (quality criteria)

2. **Ask the LLM to:**
   
   - rate the feedback along each dimension
   
   - justify each rating
   
   - provide an overall score or qualitative summary
   
   - identify missing or incorrect elements

This creates a **structured, repeatable assessment**.

## 3. Avoid self-judging: use model diversity

LLMs tend to be biased toward their own phrasing and reasoning, so cross-model evaluation helps avoid “hallucinated agreement”.

Therefore there is a need to see a **different LLM** from the one that generated the student feedback.

Alternatively, **multiple LLMs**  could be used with their ratings aggregated.

## 4. Use *structured prompts* to reduce variability

Evaluation prompts should be:

- highly structured

- explicit about scoring scales

- explicit about what is *not* allowed (e.g. inventing student work)

Example structure:

```
You are evaluating the quality of feedback generated for a student assignment.

### Inputs

- Student submission: [...]
- Assignment rubric: [...]
- Feedback to student: [...]

### Meta-feedback rubric

- LLM-as-judge rubric: [...]

### Task

Evaluate the feedback strictly using the meta-feedback rubric. 
For each criterion:

1. Provide a score from 1–5.
2. Explain your reasoning with reference to the student's actual submission and the rubric.
3. Identify specific improvements.

Output your answer in JSON.
```

## 5. Frameworks for evaluation

4 frameworks were considered for evaluating LLM generated feedback:

1. LangSmith

2. Pydantic Evals

3. TruLens

4. G-Eval

The recommendation is to use **G-Eval**

### 5.1 Recommendation justification

**5.1.1 LangSmith**

- LangSmith is part of the ecosystem around LangChain and is meant as a general evaluation & observability platform for LLM-powered applications.

- It is a **managed platform** (hosted UI, dashboards, observability, datasets, evaluation workflows) combined with a **developer toolkit** (Python SDK + APIs)

- It supports *LLM-as-judge* evaluations: you can provide a rubric / prompt and let an LLM score outputs according to that rubric. 

- Also supports human-in-the-loop annotation queues, for cases where automated evaluation isn’t enough.

- Offers dataset versioning, experiment tracking, trace logging (i.e. inputs, outputs, metadata), regression detection, and both offline (pre-deployment) and online (production) evaluation workflows.

- Free for single user, paid plan required for team.

**Strengths:** Good for production-grade evaluation pipelines, experiment tracking, reproducibility, combining automated + human evals, and monitoring over time. 
**Trade-offs:** Likely more overhead to set up; less “just code + run” than a pure library.

**5.1.2 Pydantic Evals**

- Pydantic Evals is a Python library designed to run systematic evaluations of LLM outputs (or more complex multi-agent workflows) in a **code-first** way. 

- It supports “LLM-as-judge” evaluations, but also simpler evaluators (e.g. exact-match checkers, custom logic, span-based for agent internals). 

- You define datasets, “cases”, “evaluators” (i.e. your rubric/tests), then run experiments to get scored outputs — much like unit tests, but for natural-language outputs.

- Results are programmatically accessible (so easy to integrate with CI, notebooks, version control). Optionally integrates with monitoring or logging frameworks (e.g. Logfire) for visualisation.

- Pydantic Evals is free to use.

**Strengths:** Lightweight, flexible, fully code-driven and reproducible, easy to integrate into existing Python tooling (makes sense especially if you already write Python). Good for offline evaluation / experiments.  
**Trade-offs:** Doesn’t (by itself) provide fancy dashboards or production-grade trace monitoring. For large-scale or long-running applications you might need to build around it.

**5.1.3 TruLens**

- TruLens is an open-source library for evaluating and tracing LLM applications — especially suited for agents, retrieval-augmented generation (RAG), or multi-step workflows.
- It uses a concept of *feedback functions*: modular evaluators that can check various qualitative and quantitative aspects of outputs (e.g. “groundedness,” “context relevance,” “answer relevance,” “coherence,” “toxicity,” etc.) either via heuristic or LLM-based logic. 
- It can instrument your code (even complex chains / tool-and-agent workflows) to trace steps via OpenTelemetry — so you can evaluate not only final outputs but intermediate behaviour (e.g. what context was retrieved, whether tool calls were correct, etc.) 
- You can run evaluations, aggregate metrics across runs, build a kind of leaderboard to compare different versions, and use this for continuous quality monitoring.
- TruLens is free to use.

**Strengths:** Very powerful if your LLM-based system is more than a single prompt-to-output — e.g. involves retrieval, context, tool usage, multiple steps. Good for tracing + evaluating internal logic *and* output quality. Open source, flexible, integrates with standard telemetry stacks.  
**Trade-offs:** More complexity — you need to “instrument” your code. If your use case is simple (just prompt → feedback), the added power might be overkill. Also, if you rely purely on LLM-as-judge without human validation, you carry the risk of “echo chamber” (model judging model).

5.1.4 **G-Eval**

- **G-Eval** is a component of **DeepEval**, an open-source framework specifically designed for evaluating LLM outputs using structured, rubric-based scoring. It focuses on *LLM-as-judge* patterns rather than tracing or pipeline inspection.

- It uses **evaluation templates** and **rubric definitions** (YAML or Python) to systematically score model outputs across dimensions such as accuracy, helpfulness, relevance, tone, or any custom rubric you define.

- G-Eval supports **multi-criteria scoring** out of the box and automatically extracts structured results (e.g., JSON with scores + explanations) from judge LLM responses. This removes the need for writing your own judge prompts or JSON formatting logic.

- It works with **any LLM provider** (OpenAI, Anthropic, Cohere, Llama, local models) and makes it easy to benchmark different models, prompts, or parameter settings using consistent judge criteria.

- Integrates cleanly with Python notebooks and batch pipelines, allowing evaluation of a single output or large datasets with minimal boilerplate.

- G-Eval is fully **free and open source** as part of the DeepEval ecosystem.

**Strengths:** Excellent for rubric-based evaluation and LLM-as-judge scoring. Very low overhead — simple to set up, avoids async handling, and provides automatic structured results. Ideal for evaluating natural-language outputs (e.g., feedback, summaries, reasoning steps) across multiple dimensions. Highly reproducible, model-agnostic, and accessible to non-experts.

**Trade-offs:** Focused solely on evaluation — does not include tracing of multi-step pipelines, context inspection, or observability features like LangSmith or TruLens. While powerful for scoring, it may be too limited if you need insights into *how* an answer was produced, not just whether it was good. Also inherits the general risks of LLM-as-judge methods (e.g., bias, inconsistency unless run with multiple judges or consensus methods).

## **5.2 Recommendation: G-Eval**

Reasons for selecting G-Eval:

- We are using an LLM to generate feedback on student assignments, and we plan to use another LLM to evaluate that feedback (i.e. an “LLM-as-judge” pattern). This is a **simple prompt → judged evaluation output** workflow, which aligns directly with the design philosophy of G-Eval and requires no complex instrumentation or tracing.

- G-Eval is **purpose-built for rubric-based LLM evaluations**, providing built-in support for multi-criteria scoring, judge prompts, and structured result extraction. This means we do not need to manually craft evaluator classes, JSON parsing logic, or scoring schemas.

- It offers a **lightweight and highly reproducible approach**, well-suited to Python notebooks and scripting environments where we can run periodic batch evaluations, automate scoring, and track performance across different models or prompts.

- G-Eval uses **simple YAML or Python-defined rubrics**, which makes it easy to express and evolve our meta-rubric (Accuracy, Specificity, Constructiveness, Alignment, Tone/Clarity) without needing to write custom evaluator code.

- It allows us to retain **full control over results**: every evaluation returns clean, structured data (scores and explanations) that can be exported, filtered, aggregated, or visualised as part of downstream analysis.

- G-Eval is also being **used by the AAIE LLM Training stream** and this will allow evaluation tool standardisation and associated benefits (i.e. fewer tools too learn, greater pool of students that can support each other).
